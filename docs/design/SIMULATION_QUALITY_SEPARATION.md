# 画质与模拟分离：技术方案

Date: 2026-11-27
Role: technical design / 只定义边界与迁移顺序，未实施
Baseline: `main@3153d11`
Blocks: E01-A（固定种子对照实验）必须先解决可复现性

## 结论

现在「画质」直接改变战争结果，不只是画面。要做对照实验、锦标赛、倍速模拟或任何"同一配置可复现"的玩法，必须先把**影响结果的参数**和**只影响观感的参数**分成两套配置，并让物理推进与帧率脱钩。

不建议一次重写，建议分四步、每步行为可验证。

## 1. 现状：四处耦合（已核对源码）

| # | 位置 | 行为 | 影响 |
|---|---|---|---|
| 1 | `GameConfig.get_max_active_bullets()`（`GameConfig.gd:117-124`） | 低/中/高 = 1800 / 2800 / 6000 | 同配置换画质，弹幕总容量变了 |
| 2 | `BulletPool.gd:81-89`、`97-105` | 达到上限时回收**最早生成**的活跃弹 | 弹在半路消失，占领结果改变 |
| 3 | `Turret.gd:172-194` `_burst_interval_multiplier()` | 按 `Engine.get_frames_per_second()` 分档，×1.20—×4.25 | 机器越慢，发射越慢 |
| 4 | `Turret.gd:197-209` `_max_shots_this_frame()` | FPS < 24 每帧 1 发，< 40 每帧 2 发 | **每秒发弹量随帧率变化** |
| 5 | `SaveGameCodec.gd:170`、`Main.gd:605` | 存档恢复上限取自 `get_restore_bullet_limit()`（同样随画质） | 同一存档在不同画质下恢复出不同弹幕 |

补充：`low_effect_mode` 只在 `PlayerSettingsStore.gd` 与 `SettingsPanel.gd` 命中，渲染侧没有任何接线——它是名义功能，应和本方案一起处理。

**后果**：两台性能不同的设备，相同初始配置、相同种子，也跑不出同一场战争。这不是"性能差异"，是**规则差异**。

## 2. 目标模型

三层配置，职责单一：

| 层 | 内容 | 允许随设备变？ |
|---|---|---|
| `SimulationProfile`（模拟） | 弹量上限、释放节拍曲线、物理步长、碰撞与伤害规则、恢复上限、随机种子 | **不允许** |
| `RenderProfile`（表现） | 拖尾段数、粒子、装饰层、分辨率缩放、性能 HUD 显示 | 允许 |
| `QualityBundle`（预设） | 把低/中/高映射到上面两者的一组默认值 | 允许 |

关键约定：**画质预设只能改 `RenderProfile`**；`SimulationProfile` 由「对局预设 / 玩法类型」决定，与设备无关。想跑"低配手感"的人可以显式选一个模拟预设，而不是因为手机弱就自动改变规则。

### 参数对照

| 参数 | 现状 | 目标 |
|---|---|---|
| 活跃弹上限 | 1800 / 2800 / 6000（随画质） | 模拟常量（默认 6000），画质不再参与 |
| 释放节拍 | 基础脉冲 × FPS 分档 × 队列 × 爆发量 | 基础脉冲 × 队列 × 爆发量（去掉 FPS 项） |
| 每帧最大发射 | 受 FPS 分档限制 | 改为**每固定模拟步**的最大发射，与渲染帧率无关 |
| 恢复上限 | 随画质 | 取模拟上限 |
| 拖尾/粒子/装饰 | 部分随画质 | 完全归 `RenderProfile` |

## 3. 迁移顺序（每步都可独立验收）

### 阶段 1：只抽取，不改行为

把上面五处的取值集中到 `SimulationProfile` / `RenderProfile`，默认值**等于当前值**。

验收：12 个 runner 全绿；同画质下对局表现与改动前一致（用同一张截图或同一份采样日志比对）。

### 阶段 2：去掉 FPS 项

`_burst_interval_multiplier()` 与 `_max_shots_this_frame()` 移除 `Engine.get_frames_per_second()` 分支，改为按**固定模拟步**计数。

验收：在中画质下人为把帧率压到 20 FPS，与 60 FPS 跑同一 seed，弹幕时间线一致（允许极小浮点差）。

### 阶段 3：物理与渲染解耦

子弹位移目前用 `_physics_process(delta)`（`Bullet.gd:139-156`）。要保证跨设备一致，需要固定模拟步长（例如 60Hz 定步长 + 累加器），渲染只做插值。

验收：`--fixed-fps 60` 与 `--fixed-fps 144` 两种运行方式下，同一 seed 的结算结果（占领率、摧毁时间）一致。

### 阶段 4：上限策略

上限不再随画质变之后，低端机可能真的跑不动 6000 弹。此时**降级手段只能是视觉**：拖尾缩短、粒子减少、装饰关闭、分辨率缩放；不允许回收子弹来换帧率。

验收：低配设备在 6000 弹下允许掉帧，但结算与高配一致；掉帧时不得改变弹道与占领。

## 4. 与 E01-A 的关系

E01-A 要的"固定种子基线"在阶段 2 之前**没有意义**：同一 seed、同一配置，换台机器就是另一场战争。所以顺序只能是：

1. 先做阶段 1 + 阶段 2（不改玩法，只去掉 FPS 与画质对结果的影响）
2. 再补种子入口（当前 `Main.gd:90` 直接 `randomize()`，无种子参数）
3. 然后才谈 E01-A 的对照数据

否则记录下来的基线只在当次机器上成立，无法回归。

## 5. 明确不做

- 不改物理算法、碰撞精度、伤害公式
- 不做 GPU 计算、不换渲染后端
- 不改任何玩法数值（弹速、倍率、胜利条件）
- 不为"分离"而重排目录

## 6. 风险与备选

| 风险 | 说明 | 备选 |
|---|---|---|
| 低端机掉帧严重 | 去掉回收后 6000 弹在手机上可能不可玩 | 视觉降级 + 允许模拟步降低（显式选择，不自动） |
| 固定步长引入输入延迟 | 累加器实现不当时手感变差 | 渲染插值；必要时提高模拟频率 |
| 存档兼容 | 恢复上限变化会让旧存档恢复出更多弹 | 存档版本号不变，恢复上限只放宽不收窄 |
| 改动面大 | 触及 Turret / BulletPool / GameConfig / Main | 分四步提交，每步单独可回滚 |

## 7. 开放问题

- **RNG 流**：目前事件与调色板共用全局 RNG（`EventRouletteController.gd:380,490`、`GameConfig.gd:272`），固定种子后仍需保证消费顺序稳定；是否按系统拆分独立流，待阶段 2 实测再定
- **碰撞顺序**：同一模拟步内"移动 → 碰撞 → 占领 → 回收"的顺序未文档化，弹珠互撞（E02）落地前必须定死，否则会出现阵营顺序偏差
- **性能验收口径**：现有基线来自 Godot 4.6.2（`docs/PERFORMANCE.md`），4.7 需要重测

## 9. 实测：同种子不复现（2026-11-27）

用 `scripts/tests/MatchBaselineRunner.gd` 采集：经典 40×40、中画质、`seed=12345`、`--fixed-fps 60`、每 10 秒采样一次占领数/弹量/炮台血量。

### 9.1 三次同参数运行

| 运行 | 300s 结算（0/1/2/3） | 采样摘要 |
|---|---|---|
| 1 | 529 / 291 / 372 / 408 | `1087371359` |
| 2 | 331 / 729 / 201 / 339 | `3490816745` |
| 3 | 529 / 291 / 372 / 408 → 见下注 | `3387881511` |

三次互不相同。

### 9.2 对照实验（每组两跑，45s 窗口）

| 变量 | 两跑摘要 | 是否复现 |
|---|---|---|
| 原样 | `2075610062` / `1702535487` | 否 |
| 临时把 `Turret` 的 FPS 分档固定为 999 | `2750377474` / `1939180836` | 否 |
| 加 `--max-fps 60` | `1529372386` / `106837719` | 否 |
| 同时做上面两项 | `2750377474` / `1939180836` | 否 |

（FPS 固定与帧率上限两组数据同值，说明去掉分档后 `--max-fps` 已无额外影响。）

### 9.3 结论

1. **固定种子 + 固定帧率不足以复现对局。**
2. FPS 分档是**真实但非唯一**的耦合源；把它摘掉，仍然发散。
3. 因此「先做阶段 1 + 阶段 2 就能拿到 E01-A 基线」这个判断，**被实测否掉**。

### 9.4 剩余嫌疑（未证实，按可能性排序）

| 嫌疑 | 依据 |
|---|---|
| 游戏逻辑挂在两套时钟上 | 事件计时在 `_process`（`EventRouletteController.gd:129-140`）、发射预算按帧（`Turret.gd:197-209`），子弹位移在 `_physics_process`（`Bullet.gd:139`） |
| RNG 为全局单流 | `EventRouletteController.gd:380,490`、`GameConfig.gd:272` 共用一条流，任何调用顺序差异都会放大 |
| 帧间对齐漂移 | 即使两套时钟步长都固定，同一模拟秒内的调用次数比例不固定 |

### 9.5 对方案的影响：新增阶段 0

原计划的阶段 1（抽取）→ 阶段 2（去 FPS 项）顺序不够，必须前置一个**阶段 0：单时钟定步长**：

- 把发射预算、事件计时、子弹推进放进同一个固定步进循环
- RNG 按系统分流（事件 / 调色板 / 其他），避免共用一条流
- 验收标准改为可执行的一条：**同一 seed 连续两跑，采样摘要完全一致**

阶段 0 未通过前，E01-A 记录的任何"基线数字"都不可比，只能当现象记录。
