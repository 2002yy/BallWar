# 玩法总路线：v2.2—v3.0

Date: 2026-11-27
Role: product direction input / 产品方向输入，不是发布承诺
Baseline: `main@3153d11`（标记稳定版 `v2.1.11.1`，Godot 4.7，12 个测试 runner）
Status: 成熟度评分、工期、性能目标均为设计判断；未做新构建实机试玩

结论：项目应从以工程维护为主的 v2.1 阶段，转向以体验、表现和玩法创新为主的 v2.2—v3.0 阶段。不换引擎、不推翻现有代码，也不一次性实现全部构想。

目标定位：

> 以弹珠物理、随机火力生产、领土争夺为核心，兼具自动观战、阵营构筑、自定义战争实验的轻量级物理战争沙盒。

本文与 [`GAMEPLAY_EXPANSION_RESEARCH.md`](GAMEPLAY_EXPANSION_RESEARCH.md) 的关系：研究文档回答「可以往哪扩」，本文回答「先做什么、按什么顺序、怎么判断值不值得做」。冲突时以本文为准，研究文档保留为素材库。

## 3. 倍率仓：从随机弹珠机到火力生产系统

第一优先级。现有拆分已具备承载新玩法的结构：`ControlChamber.gd`（运行与释放）、`ChamberBallPhysics.gd`（落球与钉柱）、`ChamberState.gd`（待发弹量、锁定、短路）、`ChamberRenderer.gd` / `ChamberDrawModel.gd`（绘制）、`ChamberSaveAdapter.gd`（存档）。

**落地前置条件**：`ChamberBallPhysics` 仍以左门、右门两个固定结果为基础；`pending_count` 同时存在于节点字段与 `ChamberState`。多门系统开始前必须先确定状态的唯一权威，否则新机制会放大双份数据不同步的风险。

### 3.1 四类控制仓（第一轮只做这四种，不做自由编辑器）

| 类型 | 规则 | 定位 |
|---|---|---|
| 经典型 | 传统倍率释放 | 保留原版，作为所有实验的对照 |
| 稳产型 | 稳定增加火力，减少前期等待 | 降低方差，牺牲极限爆发 |
| 储备型 | 将部分待发弹量转化为**储备资源**，用于**购买道具** | 引入局内经济 |
| 防御型 | 将部分弹量转化为**建设资源**，用于**增加己方炮塔** | 引入军事设施扩张 |

后两类是本轮修订的重点：储备型不是「存到下一轮」，防御型不是「加生命」，而是分别长出**经济系统**与**建设系统**。

### 3.2 储备型：局内道具商店

储备资源与待发弹量相互独立，转换时扣除对应弹量。储备有上限，避免无限蓄积。

| 道具 | 效果 | 示例价格 |
|---|---|---|
| 增加控制球 | 永久增加一颗控制球，提高火力生产频率 | 100 |
| 幸运爆炸 | 触发一次随机战场爆炸，范围与效果待实验 | 200 |
| 幸运倍率 | 提高下一轮待发弹量 | 150 |
| 紧急释放 | 立即释放当前积累的火力 | 80 |
| 特殊弹珠 | 获得一批具有特殊能力的弹珠 | 120 |
| 临时护盾 | 短时间保护己方炮台 | 150 |

价格未冻结，仅示意。设计原则：

- 储备与弹量分离，转换有成本
- 自动观战模式下由阵营 AI 自行决定购买什么
- 玩家干预模式下可主动购买
- 每件道具必须有明确价格、使用条件和**可见的战场反馈**
- 与随机事件并存：事件是随机获得，道具是主动购买

**第一版只实现「增加控制球」和「幸运爆炸」两项**，其余作为候选，不急着扩张。

### 3.3 防御型：多炮塔建设体系

名称暂保留「防御型」，实际定位更接近**建设型**：增加炮塔既加强防御，也扩大攻击范围、形成交叉火力。

| 炮塔 | 功能 | 开发顺序 |
|---|---|---|
| 普通辅助炮塔 | 增加发射位置 | 第一批 |
| 防御炮塔 | 优先攻击附近敌方弹珠 | 第二批 |
| 重型炮塔 | 集中火力突破敌方领土 | 第二批 |
| 散射炮塔 | 大范围覆盖战场 | 第二批 |
| 支援炮塔 | 强化附近友方设施 | 后续 |
| 超级炮塔 | 高成本大型战争设施 | 后续 |

必须先定的规则：

- 新炮塔只能建在**己方领土的合法位置**
- 炮塔可被敌方摧毁
- 有建设成本与数量上限
- **第一版所有炮塔共享阵营火力资源**，避免每加一个炮塔就凭空翻倍弹量
- 灭亡判定必须明确「主炮台被毁」与「全部炮台被毁」的区别

多炮塔各自的独立控制仓属于后续能力，第一版不做。

### 3.4 四类型差异

| 类型 | 核心优势 | 主要弱点 |
|---|---|---|
| 经典型 | 随机倍率爆发 | 火力不稳定 |
| 稳产型 | 持续稳定进攻 | 极限爆发较弱 |
| 储备型 | 道具组合、灵活发展 | 前期需要积累资源 |
| 防御型 | 多炮塔、交叉火力 | 建设成本高 |

后期可相互组合：储备型买道具换炮塔，防御型靠炮塔扩大领土控制。

### 3.5 功能钉（第二轮，多门稳定后）

| 功能钉 | 碰撞效果 |
|---|---|
| 加法钉 | 增加待发弹量 |
| 倍率钉 | 小幅提升倍率，单球单次下落限制触发次数 |
| 分裂钉 | 临时产生额外落球 |
| 弹射钉 | 改变落球路径 |
| 充能钉 | 为下一轮增加特殊炮弹 |
| 传送钉 | 将球送往其他区域 |

前提是玩家看得懂：球碰了什么、得到了什么。

第三轮才是真正的控制仓编辑（钉柱与门的战前编辑、方案保存、方案对战），不在 E01 范围。

### 3.6 实验序列 E01—E06

每个实验都必须能关闭，经典模式始终作为对照。

| 编号 | 内容 | 依赖与备注 |
|---|---|---|
| E01-A | 经典控制仓基线 | 固定种子、可复现的对照数据 |
| E01-B | 加法门与稳定火力生产 | 稳产型的基础 |
| E01-C | 储备门 + 储备资源 + 加球 / 幸运爆炸 | 只做两件道具 |
| E01-D | 建设门 + 单座辅助炮塔原型 | 触及「阵营 ↔ 炮台」一对一结构，需与 E03 协调 |
| E02 | 弹珠相互碰撞与特殊弹珠 | 先做 C1，网格分桶验证性能 |
| E03 | 完整多炮塔系统、可争夺中立设施 | 含灭亡判定与共享火力规则 |
| E04 | 物理地形与机关 | 三张地图起步 |
| E05 | 阵营构筑、道具扩展、AI 购买策略 | 依赖 E01-C 的道具框架 |
| E06 | BOSS、要塞攻防、非对称战争 | 依赖 E03 的多设施与多炮台 |

E01-D 会动到现有数据结构，先做**一座**辅助炮塔的原型，确认共享火力与灭亡判定成立，再扩成完整建设系统。

## 4. 弹珠与武器系统

现有炮弹单一：固定速度、反弹、命中敌方格子占领并消失、命中炮台扣血。

| 弹种 | 特性 |
|---|---|
| 普通弹珠 | 单格占领，低成本高数量 |
| 穿透弹珠 | 有限占领能量，连续打穿多格 |
| 重型弹珠 | 质量大，对炮台伤害高 |
| 散射弹珠 | 扇形多股弹流 |
| 集束弹珠 | 命中后分裂，局部多方向扩张 |
| 拦截弹珠 | 主要用于抵消敌方弹幕 |

平衡原则：**特殊炮弹的威力来自火力资源转换，而不是无条件变强。** 十发普通弹可合成一颗十单位能量的重弹，获得穿透，但总占领能力不凭空增长。优势来自集中火力与攻击方式，不同武器之间才有取舍。

### 4.1 弹珠互撞三阶段

| 阶段 | 内容 |
|---|---|
| C1 | 不同阵营普通弹珠碰撞后相互抵消 |
| C2 | 引入能量与质量，大弹耗能抵消小弹 |
| C3 | 偏转、反弹、拦截、特殊碰撞 |

第一版只做 C1。当前上限 6000 活跃弹，不做全量两两检测；先验证空间网格分桶，并明确同一物理步内「移动 → 碰撞 → 占领 → 回收」的顺序，否则处理顺序会带来阵营偏差。

## 5. 领土与军事设施

这是从弹珠模拟升级为战争模拟的关键。

| 设施 | 优先级 | 理由 |
|---|---|---|
| 可占领中立炮台 | P0 | 直接产生看得见的战局变化 |
| 可破坏要塞 | P1 | 区域获得不同防御价值 |
| 兵工厂 | P1 | 连接领土与火力生产 |
| 拦截塔 | P1 | 增加防御手段 |
| 修复站 | P2 | 有价值但可能拖慢结算 |
| 能源站 | P2 | 需要配套经济 |
| 主基地与供给网络 | P3 | 容易把轻量游戏变成复杂战略游戏 |

现阶段不引入矿物、金币、人口、科技点等多套资源。**只用一种火力资源**就足以验证领土经济是否有意思。

## 6. 地图与物理环境

地图不只是初始涂色，还包括：哪些区域可占领、哪些反弹、哪些改变弹速/方向、哪些设施可攻占、各阵营从哪发射。

候选：经典平原、中央要塞、迷宫、旋转、传送、引力、岛屿、狭道攻防、超级基地。

**第一版只做三张**：经典平原、中央要塞、十字反射墙，先验证地图机制值不值得继续投入。

## 7. 模式结构：从「模式爆炸」改为三层组合

现有四个模式（源码核对）：基础（最后存活炮台胜）、占领（75% 占领率）、限时（5—15 分钟按占领率结算）、狂野（×3 倍率、更频繁事件，仍按炮台歼灭结算）。狂野本质是**倍率与事件频率的预设**，不是独立胜负机制；若继续按「六国狂野 / 八国狂野 / 限时狂野」铺开，会产生大量重复模式。

改为三层：

| 层 | 取值 |
|---|---|
| 玩法类型 | 经典战争 / 设施争霸 / 阵营构筑 / 要塞攻防 / BOSS 讨伐 / 自由沙盒 |
| 胜利条件 | 歼灭 / 占领 / 限时 |
| 规则预设 | 标准 / 快速 / 狂野 / 自定义 |

另加两个独立轴：玩家参与方式（观战 / 自由干预 / 支持一方）、地图。BOSS 等特殊模式的胜利条件需单独约束，不能简单套用三种胜负。

### 目标产品结构与建议版本

| 模式 | 核心体验 | 建议版本 |
|---|---|---|
| 经典战争 | 原版四阵营弹珠战争 | v2.2 |
| 自由沙盒（基础版） | 配置现有规则、火力、地图 | v2.3 |
| 设施争霸 | 争夺中立炮台与战略设施 | v2.4 |
| 阵营构筑 | 局内强化与火力流派 | v2.5 |
| 要塞攻防 | 非对称攻防 | v2.6 |
| BOSS 讨伐 | 多阵营合作或竞争 | v2.6 |
| 史诗战争 | 多阵营、大规模高密度弹幕 | v2.7 |
| 自定义战争实验室 | 地图、控制仓、武器编辑 | v3.0 |

版本号是规划建议，不是仓库既定发布承诺。

## 8. 美术与音频

### 8.1 视觉方向

配色不等于风格。先定一个主风格，再允许换肤。

- **主风格：霓虹机械战争** — 深色战场、明亮能量弹珠、机械炮台、动态领土边缘。重点是战斗清晰、弹幕醒目，不是大面积发光。
- **备选皮肤：糖果弹珠机** — 保留现有活泼配色，加强玻璃弹珠与玩具质感。
- **备选皮肤：军事沙盘** — 服务要塞攻防、史诗战争与战争实验室，突出设施与战线。

### 8.2 资源清单

| 类别 | 内容 | 优先级 |
|---|---|---|
| 弹珠 | 普通、重型、穿透、拦截、集束 | P0 |
| 炮台 | 底座、旋转炮管、损坏层、残骸 | P0 |
| 控制仓 | 玻璃面板、金属钉、倍率门、机械边框 | P0 |
| 战场 | 网格、动态边界、占领效果 | P0 |
| 特效 | 炮口闪光、碰撞火花、摧毁、护盾 | P0 |
| 音效 | 落球、倍率、释放、占领、爆炸 | P0 |
| UI | 统一按钮、面板、字体、图标 | P1 |
| 军事设施 | 要塞、兵工厂、拦截塔、修复站 | P1 |
| 地图机关 | 反射墙、传送门、引力装置 | P1 |
| 背景 | 主题背景、环境装饰 | P2 |

**炮台优先升级**，且应拆件：底座、炮管、能源核心、护盾层、损坏层、残骸。单张固定贴图无法表现旋转瞄准、后坐、过热、受击和爆炸。

**不重新收集大量素材**：仓库已有 Kenney 科幻 UI、Wenrexa、Game-Icons 与筛选过的音效。先用现有素材做出一个可玩的美术样板。外部素材只补缺口（Kenney Rolling Ball / Particle Pack / UI Pack Sci-Fi / Top-down Tanks、ambientCG、Game-Icons），采用前仍需逐个核查授权与署名要求。

### 8.3 音频

仓库已有音效文件，但主要战斗与 UI 路径上仍没有统一的音频播放系统（源码核对：`low_effect_mode` 与音效均未见运行时接线）。声音不是附加项：它让玩家不用盯着控制仓也知道某方在攒火力。

| 行为 | 反馈 |
|---|---|
| 落球撞钉 | 清脆、低音量 |
| 倍率增长 | 随倍率升高的音阶 |
| 大规模蓄能 | 逐渐增强的能量声 |
| 炮台释放 | 按规模调整的连续火力声 |
| 弹珠相撞 | 短促碰撞声 |
| 领土占领 | 高频低音量，按批次合并 |
| 炮台低血量 | 危险提示 |
| 炮台摧毁 | 爆炸与机械停机 |
| 胜利 | 短胜利音乐 |

必须有并发上限与触发频率限制——3000 颗炮弹同时独立播声是不可接受的。

## 9. UI 与操作

### 9.1 当前问题的来源

基线画布 1120×720（`project.godot`）；`LayoutProfiles` / `LayoutCoordinator` 按地图尺寸给位置，部分 Y 坐标靠人工调校；`GameHUD.tscn` 的比分条是固定的四分色段（Blue/Red/…）。这在四阵营时代能工作，但撑不住六/八阵营与复杂设施。

### 9.2 分层

| 层 | 内容 |
|---|---|
| 主菜单 | 四个主入口；模式、地图、画质、存档槽从主页面逐步移出 |
| 战斗 HUD 一层 | 战场、炮台、弹幕 |
| 二层 | 阵营占领率、生命、待释放火力 |
| 三层 | 事件、战况、暂停、速度 |
| 四层 | 详细日志、性能数据、调试（默认隐藏） |

阵营数超过四个后，不能继续把每个控制仓固定摆在地图四周，应改为「阵营列表 + 当前选中控制仓」。

### 9.3 结算

在现有（时长、最终占领率、峰值弹量、事件次数）之上补战局回顾：最大单轮发射、最低占领率、摧毁炮台数、领先方更替次数。结算页要能回答：谁赢了、怎么赢的、转折在哪。

## 10. 架构演化

问题不是脚本数量，而是**数据模型绑定四阵营、单一炮弹、双门控制仓**。

### 10.1 扩展瓶颈（已核对源码）

| 现状 | 影响 |
|---|---|
| `Main.gd` 743 行 | 仍承担部分战斗事件编排、UI 与存档协调 |
| `ControlChamber.gd` 629 行 | 新门、功能钉、状态同步会继续加复杂度 |
| `BulletPool.gd` 478 行 | 对象管理、渲染压力与性能统计混在一起 |
| `GameConfig` 全局静态配置 | 不支持不同阵营不同属性 |
| `GameSceneBuilder` 固定四阵营位置 | 六/八阵营、BOSS 需扩展 |
| `Battlefield` 写死 `{0,1,2,3}` 归属与 `clampi(..,0,3)` | 中立格、设施、障碍无法只靠配置加入 |
| `GameHUD` 固定四分色段 | 多阵营 HUD 需数据驱动 |
| `EventRouletteController` 固定四阵营候选 | 联盟、复活、BOSS 需改动 |
| `SaveGameCodec` 依赖现有实体字段 | 新武器、储备仓、设施需处理存档兼容 |

### 10.2 需要优先处理：画质会改变战斗结果

已核对源码：低/中/高画质的活跃弹上限分别 1800 / 2800 / 6000；达到上限后 `BulletPool` 回收最早生成的弹；释放间隔随 FPS 与队列压力调整；存档恢复的子弹数量也与画质相关。

后果：两台性能不同的设备，即使初始配置与随机种子相同，也无法保证产生相同的战争过程。

过去为保性能可以理解，但公平实验、锦标赛、倍速模拟、沙盒对照都要求先分离「模拟规则」与「画面质量」：

| 模拟规则（影响结果） | 画面设置（不影响结果） |
|---|---|
| 弹量上限、释放速度、物理更新频率、碰撞与伤害规则、随机种子 | 拖尾数量、粒子、光效材质、装饰层、显示帧率 |

同时 `low_effect_mode` 目前只有存储项与设置面板，未接到渲染系统——属于名义功能，应与新视觉设置一起解决，而不是继续留着。

### 10.3 目标分层

| 层 | 负责 |
|---|---|
| 配置 | 本局有哪些阵营、地图、武器、胜利条件 |
| 状态 | 领土归属、炮台生命、弹珠、倍率与储备 |
| 模拟 | 移动、碰撞、占领、伤害、释放 |
| 表现 | 按状态绘制与播放 |
| UI | 展示信息、提交操作 |
| 存档 | 持久化必要的战斗状态 |

新玩法优先用 `Resource` 或明确配置结构表达，不继续往 `GameConfig` 堆全局静态变量。

**不专门做一次目录大迁移**，只在改到相关功能时顺手整理：

| 新功能 | 同时进行的必要调整 |
|---|---|
| 多门控制仓 | 统一仓内状态来源、门类型数据化 |
| 特殊弹珠 | 炮弹属性配置与命中规则 |
| 弹珠互撞 | 物理步内的碰撞解决顺序 |
| 中立设施 | 区分格子归属 / 地形 / 设施状态 |
| 多炮台 | 阵营与炮台一对一 → 一对多 |
| 多阵营 | 阵营集合替代固定枚举遍历 |
| 地图编辑器 | 地图资源化、配置可保存 |
| 多模式 | 胜负规则、战斗规则、对局预设三者组合 |

## 11. 性能与规模

当前性能基线来自 **Godot 4.6.2**（四炮台高压：均 120 FPS / 最低 10 FPS），不能作为 4.7 主线的证明；加入弹珠互撞、设施、动态边界后瓶颈也会迁移。

### 规模阶梯

| 级别 | 活跃弹珠 | 技术路线 |
|---|---|---|
| S0 现有中画质 | 2,800 | 保留对象池 + 局部碰撞检测 |
| S1 现有高画质 | 6,000 | 同上，先测清 CPU 开销 |
| S2 扩展模拟 | 10,000 | 物理循环、数据布局、批量绘制 |
| S3 大规模 | 20,000 | 集中管理弹状态、MultiMesh 实例化 |
| S4 史诗实验 | 50,000 | 评估 GDExtension / GPU 计算 / 独立后端 |

当前用 GL Compatibility 渲染器；走 RenderingDevice GPU Compute 需评估后端切换代价与 Android 兼容性。第一轮先测 CPU 物理与节点管理，不先上 GPU。

### 验收目标（建议值，未实测）

- PC：1080p / 60 FPS，重点看帧时间波动
- Android：≥30 FPS，按真机实测调整
- 同一模拟预设在低/高画质下核心规则一致
- 连续高压 10 分钟，查内存、队列堆积、卡顿、存档恢复
- 记录平均帧率、1% Low、P95/P99 帧时间、碰撞耗时、峰值弹量

## 15. 总控裁定

1. **战斗好看**：提高火力密度、表现弹幕交锋、制造清晰的战线变化
2. **每局不同**：倍率仓、武器、地图、设施共同产生不同战争过程
3. **玩家创造战争**：可配置阵营、规则、武器、战场，而不只是选预设模式
4. **规模与稳定**：前三个成立后再扩规模与设备覆盖

下一版最大的变化不该是代码少了几百行或菜单多了几项，而是打开新版时能立刻感觉到：这不再是四个炮台慢慢涂色，而是有火力爆发、物理交锋、攻防转换和意外逆转的弹珠战争。
